# Тестирующая система

Описание проверки решений в демо. Код: [`assets/js/judge/`](../assets/js/judge), тесты: [`tests/`](../tests). Теоретическая основа — исследования в `research/06_quantum_autograder_research` и `academic_paper_quantum_autograder` в основной библиотеке проекта.

**Статус: демо.** Проверка работает в браузере участника. Набор тестов лежит в исходном коде и виден любому, кто откроет репозиторий. В боевой версии тесты должны исполняться на сервере (см. [ROADMAP.md](ROADMAP.md)). Всё ниже — про то, что реализовано сейчас.

## Почему не «запустить и сравнить»

В классическом соревновательном программировании проверка — сравнение вывода. В квантовом так не работает:

1. **Глобальная фаза не наблюдаема.** Схемы, отличающиеся множителем `e^{iφ}`, физически одинаковы, и система обязана считать их равными.
2. **Но относительные фазы между входами наблюдаемы.** Если проверять каждый вход «с точностью до своей фазы», пропустится схема, которая верна на каждом базисном входе, но неверна как преобразование (например, CX вместо CZ).
3. **Вспомогательные кубиты.** Неочищенная анцилла разрушает интерференцию, если оракул встроен в более крупный алгоритм. Сравнение «только вектора данных» её пропускает, а сравнение «всего вектора» бракует верное решение с чистыми анциллами у эталона с другим их числом.
4. **Размер.** Вектор состояния растёт как `2^n`, матрица преобразования — как `4^n`.
5. **Нечестные решения.** Раздутые схемы, лишние гейты, нарушение базиса и связности.

## Каскад проверок

```
код / схема ──► построение схемы ──► ограничения ──► входы ──► шум ──► вердикт
                 (интерпретатор)      (дёшево)      (симуляция)  (относительно эталона)
```

| Шаг | Что проверяется | Вердикты |
|-----|-----------------|----------|
| Построение | Код выполняется интерпретатором Qiskit-lite; схема построена. Ошибка — попытка не засчитывается, штрафа нет. | `ошибка в коде · строка N` |
| Ограничения | Число гейтов, глубина (ASAP-слои), число двухкубитных гейтов, вызовы оракула, базис, связность, число кубитов. Схема, раздутая более чем в 4 раза над лимитом гейтов, не симулируется. | `лимит гейтов`, `превышена глубина`, `гейт вне базиса`, `нарушена связность`, `число кубитов` |
| Входы | Каждый случай набора: схема применяется к входному состоянию, результат сравнивается с ожидаемым. | `неверный ответ · тест k` |
| Шум | Фиделити схемы участника с деполяризующим шумом сравнивается с фиделити эталона. | `не выдержал шум` |

Приоритет вердиктов: **неверный ответ** > **лимит** > **шум**. Если состояние неверно, лимиты не обсуждаются; если состояние верно, но лимиты нарушены — вердикт «лимит» (в банке отправка до этого блокируется интерфейсом, в раундах получает вердикт и штраф).

## Случаи набора

Задача объявляет `suite(param)` → `{ n, cases }`. Случай описывает вход и ожидание:

| Вид ожидания | Проверка | Где используется |
|--------------|----------|------------------|
| `state` | Фиделити с целевым чистым состоянием `F = |⟨target|out⟩|² ≥ 1 − 10⁻⁶` на всех кубитах или на подсистеме (остальные — «не важно», считается след) | подготовка состояний, преобразования, телепортация |
| `dist` | Расстояние полной вариации распределения исходов подсистемы до ожидаемого | измерения в базисах X/Y, swap-тест |
| `prob` | Вероятность одного исхода в заданных границах | Дойч — Йожа, Бернштейн — Вазирани, Гровер, оценка фазы |

Случаи с общей меткой `group` образуют **одно унитарное преобразование**: у перекрытий `⟨expected|out⟩` должна совпадать общая фаза (допуск 10⁻⁴ рад). Так ловятся схемы, верные на каждом входе по отдельности, но не как оператор.

Конструкторы наборов (`assets/js/judge/builders.js`):

- `stateSuite` — одно состояние из `|0…0⟩`;
- `mapSuite` — изометрия `|x⟩ ↦ ±|g(x)⟩` на подмножестве кубитов: все базисные входы (до 64) и случайные суперпозиции с общей фазой;
- `xorOracleSuite`, `phaseOracleSuite` — оракулы `|x⟩|y⟩ → |x⟩|y ⊕ f(x)⟩` и `|x⟩ → (−1)^{f(x)}|x⟩`; анциллы остаются вне входов, то есть обязаны вернуться в `|0⟩`;
- `refSuite` — ожидание задаётся функцией над состоянием (QFT, код Шора);
- `subsystemSuite` — проверка только подсистемы (телепортация);
- `bitOracle`, `markOracle` — «чёрные ящики» для задач на алгоритмы.

## Анциллы

Вспомогательные кубиты — это кубиты вне `inQubits` набора: они подаются в `|0⟩`, а ожидаемое состояние их тоже содержит в `|0⟩`. Поэтому:

- неочищенный мусор даёт `F < 1` на полном векторе;
- при провале судья вычисляет вероятность `|0…0⟩` на анциллах и, если она ниже 99,9 %, добавляет подсказку «вспомогательные кубиты остались не в |0⟩».

Это соответствует **строгому развычислению** (категория A в формализации эквивалентности на подпространстве). «Грязные» анциллы (заимствование) в демо не поддерживаются.

## Шум

Модель: деполяризующий канал `ρ → (1−p)ρ + p · (I/2 ⊗ Tr_q ρ)` после каждого гейта на каждом затронутом кубите, `p = ε` для гейтов на двух и более кубитах, `p = ε/10` для однокубитных. Расчёт — на матрице плотности (2n кубитов в векторном представлении), n ≤ 7.

Критерий: `F(участник) ≥ F(эталон) − slack` при том же шуме. Так шум наказывает лишние гейты, не требуя абсолютного порога. В банке шум выключен (кроме задач, где он часть условия: «Белл в шумном канале»), в раундах `ε = 1 %`.

## Что реализовано в симуляторе

| Возможность | Статус |
|-------------|--------|
| Вектор состояния, до 12 кубитов в коде, до 8 в песочнице | есть |
| Управляемые варианты любых однокубитных гейтов и SWAP, произвольное число управлений | есть |
| Матрица плотности: шум, сброс, промежуточные измерения | есть |
| Оракулы-«чёрные ящики» в задачах | есть |
| Динамические схемы с классическим управлением (`c_if`) | нет; в задачах используется принцип отложенного измерения |
| Символьная эквивалентность (ZX-исчисление, QCEC, диаграммы решений) | нет — только численная симуляция |
| Проверка на реальном железе | нет |

## Интерпретатор Qiskit-lite

Режим «код» исполняет подмножество Python, а не настоящий Python и не настоящий Qiskit ([`assets/js/lang/`](../assets/js/lang)):

- поддерживается: числа, строки, списки, `for`, `while`, `if`, `def`/`return`, генераторы списков, срезы, арифметика и битовые операции, `range/len/min/max/sum/...`, модули `math` и `numpy` (мини-версии);
- `QuantumCircuit`, `QuantumRegister`, методы `h x y z s sdg t tdg sx p rx ry rz cx cy cz ch ccx ccz cp crx cry crz swap cswap mcx mcp measure reset append compose inverse copy depth size`;
- платформенный оракул — глобальное имя `oracle`: `qc.append(oracle, [0, 1, 2])`;
- нет `eval`, нет доступа к DOM и сети, лимит на число шагов (1,5 млн), на размер `range`, на число операций (5000), на число кубитов (12);
- сообщения об ошибках — на русском, с номером строки и подсказкой (`cnot → qc.cx(0, 1)`).

Различия с настоящим Qiskit: нет f-строк, классов, импортов сторонних модулей; `pi` нужно импортировать (`from math import pi`), как в Python.

## Проверка самой системы

`npm test` (или `node --test tests/*.test.mjs`) запускает:

- проверку эталонных решений всех задач (каждое должно получать «принято»);
- проверку, что пустая схема и эталон без последнего гейта **не** проходят;
- негативные случаи судьи: лишний `Z`, CX вместо CZ, мусор в анцилле, наивная цепочка GHZ, лишние CX при шуме, приоритет вердиктов;
- интерпретатор и симулятор: форматы состояний, разложение Тоффоли, сообщения об ошибках, шум.
