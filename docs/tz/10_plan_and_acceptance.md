# 10. Этапы, приёмка, перенос с демо, риски

[← к оглавлению](README.md)

## 10.1. Этапы

**[Д]** Сроки рассчитаны на команду из 3–5 разработчиков и приведены в неделях от старта; их нужно пересчитать
под реальный состав. Порядок этапов важнее дат: каждый заканчивается работающим результатом, который можно
показать.

| Этап | Недели | Результат | Что входит |
|---|:-:|---|---|
| 0. Основа | 1–2 | пустой каркас развёрнут на проверочном окружении | репозиторий, окружения, CI, выкладка; пакет дизайн-системы с токенами и шрифтами; витрина компонентов |
| 1. Сайт на настоящих адресах | 3–6 | многостраничный сайт выглядит как демо, данные идут с сервера | перенос компонентов и страниц; пакеты `quantum-core`, `qiskit-lite`, `board`; аккаунты и вход; банк задач из базы; импорт пакетов; редактор задачи с локальной проверкой примеров; песочница с короткими ссылками |
| 2. Серверная проверка | 5–9 | отправка получает вердикт с сервера | очередь, судья `numeric-v1`, исполнитель с изоляцией, непрозрачные оракулы, статусы в реальном времени, страница отправки, прогресс и профиль, ограничения частоты |
| 3. Раунды и рейтинг | 8–12 | закрытая бета: раунд на 100 участников | раунды, регистрация, таблица, вопросы жюри, рейтинг, пульт раунда, уведомления, участие «с таймером» |
| 4. Готовность к запуску | 11–16 | открытый запуск на ступени «Запуск» | нагрузочные испытания, наблюдаемость и регламент, внешняя проверка безопасности, мобильная версия, доступность, авторский контур с ревью, юридические документы |
| 5. После запуска | далее | — | экзаменационный режим; параметрический уровень судьи; развитие симулятора; английский язык |

Этапы 1 и 2, 2 и 3 перекрываются: вёрстка страниц раундов идёт параллельно с судьёй.

Параллельно с разработкой, вне этого ТЗ: ревью задач банка вторым экспертом; закрытые сетки тестов; мобильные
макеты; тексты политики и согласий.

## 10.2. Критерии приёмки по этапам

### Этап 0

- Команда `make dev` (или аналог) поднимает весь стек локально с тестовыми данными.
- Правка в основной ветке автоматически попадает на проверочное окружение.
- Витрина компонентов открывается; токены совпадают с [`assets/css/tokens.css`](../../assets/css/tokens.css).

### Этап 1

- Все адреса из карты сайта (раздел 1.3), кроме раундов и отправок, открываются по прямой ссылке и после
  обновления страницы.
- Приёмка дизайна по разделу 2.7 пройдена для главной, входа, банка, задачи, песочницы, профиля, настроек.
- 61 задача ядра импортирована; страница каждой открывается, формулы отрисованы, фильтры банка работают по
  полям карточки.
- Автоматический тест утечек: в ответах открытого API нет полей закрытой части и фрагментов эталонов.
- Тесты демо на перенесённых пакетах проходят; набор сверки браузера и сервера (раздел 7.6) проходит.
- Гость собирает схему, регистрируется, и черновик сохраняется за аккаунтом.

### Этап 2

- Приёмка заглушки судьи (раздел 6.7): 61 эталон получает «принято» (SA-044 — 100 баллов), 74 неверных
  решения — ожидаемые вердикты, через полный конвейер.
- Повтор запроса с тем же ключом идемпотентности не создаёт вторую отправку.
- Остановка исполнителя посреди проверки не теряет отправку и не даёт двух разных вердиктов.
- Набор враждебных решений не выходит из исполнителя и не влияет на соседние проверки: бесконечный цикл,
  расход памяти, порождение процессов, запись в файловую систему, обращение в сеть, чтение окружения, чтение
  определения оракула.
- Вердикт приходит в интерфейс без перезагрузки; при отключённом потоке событий работает опрос.
- Время до вердикта: 95 % — до 5 секунд при потоке 5 отправок в секунду.

### Этап 3

- Пробный раунд на 100 участников закрытой беты проведён по регламенту (раздел 9.7) три раза.
- Таблица в Redis совпадает с пересчётом по базе после каждого раунда.
- Перепроверка задачи после конца раунда пересчитывает таблицу и рейтинг; откат рейтинга раунда работает.
- Часы участника, переведённые на час, не влияют ни на обратный отсчёт, ни на время отправки.
- Участие «с таймером» не меняет мест исходного раунда и рейтинг.

### Этап 4

- Нагрузочные испытания (раздел 3.5) пройдены на ступени «Запуск» с двукратным запасом: 2 000 участников в
  раунде.
- Показатели надёжности (раздел 3.4) выполнены; восстановление из резервной копии проверено.
- Внешняя проверка безопасности пройдена, критических замечаний нет.
- Приёмка дизайна пройдена на всех страницах и пяти ширинах; автоматическая проверка контраста и доступности
  без ошибок.
- Юридические документы опубликованы; выгрузка и удаление данных работают.

## 10.3. Перенос с демо

| Что | Как |
|---|---|
| Сайт демо | остаётся на GitHub Pages как архивная версия с пометкой и ссылкой на платформу; не развивается |
| Дизайн | переносится полностью — раздел 2 |
| Код симулятора, интерпретатора, доски | переносится пакетами — раздел 7.3 |
| Браузерный судья | остаётся для проверки открытых примеров — раздел 6.9 |
| Задачи демо | 43 задачи разложены по новой классификации в [`bank/LEGACY.md`](../../bank/LEGACY.md); на платформу попадают как пакеты банка, не автоматически |
| Аккаунты и прогресс демо | не переносятся: они хранятся в браузерах. На странице входа платформы — пояснение для пришедших с демо |
| Ссылки песочницы | длинные ссылки со схемой в адресе продолжают работать |
| Смоделированные участники, раунды, счётчики | удаляются |
| Формулы рейтинга и штрафов | переносятся как параметры — раздел 8 |
| Тесты | [`tests/`](../../tests) переносятся вместе с пакетами; тесты смоделированных раундов заменяются тестами настоящих |

## 10.4. Риски

| Риск | Вероятность | Последствие | Что делаем |
|---|:-:|---|---|
| Выход из исполнителя судьи | низкая | компрометация платформы | изоляция уровня микровиртуальной машины, отсутствие секретов в исполнителе, внешняя проверка |
| Утечка закрытых тестов | средняя | обесценивание раундов | раздельное хранение, автоматический тест утечек, закрытая сетка вне открытого репозитория |
| Очередь не справляется в конце раунда | средняя | недоверие участников | расчёт и испытания (раздел 3), масштабирование по расписанию, право жюри продлить раунд |
| Расхождение браузерного и серверного подсчёта | высокая | жалобы «у меня проходит» | набор сверки в CI, подпись «предварительно», единые определения |
| Потеря дизайна при переносе на фреймворк | средняя | главный актив демо размыт | витрина, сравнение снимков, приёмка по разделу 2.7 до функциональной приёмки |
| Численный судья пропускает решение, неверное на больших $n$ | средняя | неверные «принято» | закрытые сетки с разными размерами, поле `guarantee`, параметрический уровень для задач из поддерживаемого фрагмента |
| Параметрический уровень покрывает мало задач | высокая — подтверждено замером (раздел 6.8) | ожидания от «проверки для всех $n$» не оправдаются | численный уровень как постоянная часть каскада; стиль эталонов; расширение фрагмента — в научной части |
| Задачи банка не прошли ревью | высокая | ошибки в условиях на раунде | ревью вторым экспертом до публикации — обязательный статус `reviewed`; пробный запуск раунда |
| Формула рейтинга дрейфует | средняя | недоверие к рейтингу | формула по составу раунда, прогон на истории беты, версионирование (раздел 8.6) |
| Решения, принятые на созвонах, расходятся с этим ТЗ | высокая | переделки | таблица допущений в [`README.md`](README.md) сверяется с командой до начала этапа 1 |
| Требования закона о персональных данных | средняя | блокировка, штрафы | размещение в РФ, согласия, проверка юристом до запуска |

## 10.5. Что решить до начала работ

1. Подтвердить или исправить десять допущений из [`README.md`](README.md).
2. Выдать разработчикам доступ к Figma и назначить дизайнера, который принимает перенос и рисует недостающие
   экраны: мобильные, состояние «в очереди», страницы без макета.
3. Выбрать облако и завести окружения.
4. Решить, где хранится закрытая часть пакетов задач (раздел 4.5).
5. Назначить вторых экспертов для ревью банка и определить, какие задачи нужны к закрытой бете.
6. Выбрать формулу рейтинга (раздел 8.6).
7. Определить владельца регламента дня раунда.
