# 9. Безопасность, административный контур, эксплуатация

[← к оглавлению](README.md)

## 9.1. Аккаунты и вход

| Требование | Решение |
|---|---|
| Вход по почте | пароль хранится хэшем Argon2id; длина от 8 символов; проверка по списку утёкших паролей |
| Подтверждение почты | письмо со ссылкой; без подтверждения нельзя участвовать в рейтинговых раундах |
| Внешний вход | Яндекс ID и VK ID по OAuth 2.0 с проверкой `state` и PKCE; привязка нескольких способов к одному аккаунту **[Д]** |
| Сессия | случайный идентификатор в куке `HttpOnly`, `Secure`, `SameSite=Lax`; сессия хранится на сервере, отзывается при смене пароля; срок 30 дней со скользящим продлением |
| Восстановление пароля | одноразовая ссылка на 30 минут; ответ одинаков для существующей и несуществующей почты |
| Подбор пароля | ограничение частоты (раздел 5.5), задержка после неудач |
| Двухфакторный вход | обязателен для ролей жюри и администратора |

Вход демо (SHA-256 с солью в `localStorage`, [`assets/js/store.js`](../../assets/js/store.js)) — имитация и
в платформу не переносится. Аккаунты демо не мигрируют: они существуют только в браузерах пользователей.

## 9.3. Защита приложения

1. **Внедрение разметки.** Условия, разборы, имена пользователей, вопросы жюри выводятся только через
   экранирование. Markdown условий преобразуется на сервере при импорте с белым списком тегов; формулы
   отрисовываются на сервере. Пользовательский текст (имя, вопрос жюри) Markdown не поддерживает.
2. **Политика содержимого.** Заголовок Content-Security-Policy без `unsafe-inline` для скриптов; шрифты и
   скрипты — только со своего домена, как в демо.
3. **Подделка запросов.** Кука `SameSite` и проверка заголовка происхождения на изменяющих запросах.
4. **Внедрение в запросы к базе.** Только параметризованные запросы.
5. **Загрузка файлов.** Аватар: проверка типа и размера, перекодирование на сервере, раздача с отдельного
   домена.
6. **Исполнение чужого кода.** Только в исполнителе судьи — раздел 6.5. В API и веб-сервере код участника не
   исполняется никогда, включая «предпросмотр».
7. **Секреты.** В хранилище секретов облака; в репозитории и образах их нет. Исполнитель судьи секретов не
   получает.
8. **Зависимости.** Автоматическая проверка уязвимостей при сборке; фиксированные версии.
9. **Журнал действий.** Все действия ролей выше участника и все входы — в `audit_log`; хранение год.
10. **Внешняя проверка.** Перед открытым запуском — проверка на проникновение сторонней командой, отдельно —
    попытка выхода из исполнителя судьи.

## 9.4. Персональные данные

**[Д]** Требует проверки юристом.

- Платформа обрабатывает персональные данные граждан РФ: почта, имя, вуз, адреса входа. По закону 152-ФЗ базы
  с такими данными размещаются в РФ — отсюда выбор российского облака (раздел 3.2).
- При регистрации — согласие на обработку и ссылка на политику; отдельная галочка на публикацию имени и вуза
  в рейтинге.
- Участник может выгрузить свои данные (`GET /me/export`) и удалить аккаунт. Удаление обезличивает строку:
  отправки и места в раундах остаются под именем «удалённый участник», чтобы таблицы прошедших раундов не
  менялись.
- В журналы, метрики и сообщения об ошибках почта и имя не попадают — только внутренний идентификатор.
- Несовершеннолетние участники (школьники, НТО) — отдельный вопрос согласия родителей; решить до запуска.

## 9.5. Административный контур

Интерфейс по адресу `/admin`, собранный из компонентов дизайн-системы; отдельного дизайна не требует.

### Банк и авторский контур

| Экран | Что на нём |
|---|---|
| Задачи | список со статусами жизненного цикла (`draft`, `reference`, `reviewed`, `published`, `archived`), фильтры по дереву, автору, уровню |
| Задача | версии; для каждой — открытая часть глазами участника, закрытая часть, результат импорта: эталон и каждое неверное решение с вердиктом боевого судьи, принят ли эталон параметрическим уровнем |
| Сравнение версий | что изменилось; требуется ли перепроверка |
| Ревью | назначение второго эксперта; он решает задачу вслепую в обычном редакторе, его отправки помечены; после — заключение и перевод в `reviewed` |
| Статистика задачи | доля решивших, распределение вердиктов, медианное время до решения, самые частые ошибки — основа для калибровки уровня |
| Резерв | идеи из [`bank/reserve/reserve.yaml`](../../bank/reserve/reserve.yaml): статус, ответственный, ссылка на пакет, когда появится |
| Дерево | ветви и число задач; пустые ветви и перекосы по уровням |

Загрузка версии — через импорт из репозитория (раздел 4.5). Редактирования условий прямо в административном
интерфейсе нет: иначе репозиторий перестанет быть источником правды.

### Раунды

Создание раунда, набор задач, правила, пробный запуск, объявление; пульт дня раунда (раздел 8.4): очередь,
вердикты, вопросы, объявления, продление, перепроверка, дисквалификации; подведение итогов.

### Пользователи и платформа

Поиск пользователя, роли, блокировка с причиной и сроком, объединение дубликатов, справочник вузов; состояние
сервисов; флаги возможностей (раздел 7.5); журнал действий.

## 9.6. Наблюдаемость

| Что измеряется | Сигнал дежурному |
|---|---|
| Доля ошибок и время ответа API по адресам | ошибок больше 1 % за 5 минут; 95-й перцентиль больше 1 с |
| Длина очереди проверки и возраст самой старой отправки | возраст больше 60 с вне раунда, больше 120 с в раунде |
| Время проверки по задачам, доля `IE` | любая `IE` в раунде; доля больше 0,5 % вне раунда |
| Число живых исполнителей, перезапуски | меньше заданного минимума |
| Отставание реплики базы, место на диске, соединения | отставание больше 30 с; свободно меньше 20 % |
| Число подключений к потоку событий, задержка доставки | задержка больше 5 с |
| Расхождение таблицы раунда в Redis и пересчёта по базе | любое расхождение |
| Счётчики продукта: регистрации, первые решения, отправки | резкое падение |

Журналы — структурированные, с идентификатором запроса, который проходит от браузера до исполнителя судьи: по
одному идентификатору отправки можно собрать весь её путь. Публичная страница `/status` показывает состояние
сервисов и оценку ожидания в очереди.

## 9.7. Регламент дня раунда

1. За сутки: заморозка выкладок; пробный запуск раунда; проверка резервной копии.
2. За час: прогрев кэша условий; увеличение числа исполнителей; дежурные на связи — один по платформе, один
   от жюри.
3. Во время: пульт раунда открыт; решения о продлении и снятии задач принимает жюри; технические действия —
   дежурный по платформе.
4. Авария проверки дольше 10 минут: объявление участникам, продление на время простоя; дольше 30 минут —
   раунд нерейтинговый.
5. После: подведение итогов, разбор происшествий в течение трёх дней, правки в этот регламент.

Регламент отрабатывается на закрытой бете не менее трёх раз до открытого запуска.
